## 무엇을 했나 (평이한 요약 먼저)

카메라마다 하던 scene reconstruction 을 **depth 한 번 올리고 GPU 에서 끝낸다.** 예전에는 카메라마다 numpy 로 full-res
역투영 (≈ 17–30 만 점) → `np.unique` voxel downsample → 점 12 MB 를 GPU 로 올려 self-filter (B2) → 픽셀 마스크로 voxel
cloud 를 자르고 → attention 맵을 640×480 전체로 resample 했다. 이제 depth (float64 2.4 MB) 를 한 번 올리면 역투영 · voxel
대표점 · cap · self-filter 마스크 · 자르기가 모두 GPU 에서 일어나고, CPU 소비자가 실제로 쓰는 것 (카메라별 voxel cloud 의
점 + 픽셀 ≈ 1.3 MB, `(H, W)` 로봇 마스크 0.3 MB, 몇 개의 수) 만 내려온다. 같은 GPU depth 에 마스크를 적용한 것이 그대로 cuRobo
TSDF 의 입력이 된다 (B3 의 builder 쪽 업로드도 없어짐). 구 FK 는 청크당 한 번 (세 카메라 q 동일). attention 은 cloud 가 쓰는
픽셀만 계산한다. 지지면 RANSAC 은 가설 생성 (numpy RNG) 을 그대로 두고 (점 × 가설) inlier 세기만 GPU 로 옮겼다.

**결과는 예전과 비트 단위로 같다** — 재생 75 청크의 카메라별 cloud · 마스크 · fused cloud (CSR 전부) · 지지면 (normal ·
offset · inlier 집합) · cluster · 조작 대상 · ESDF tier · refined actions · verdict · 기록 npz 가 모두 같고, 기준선 둘도 소수점 ·
sha1 까지 같다. 청크당 AG3S+TO 중앙 **840 → 272 ms** (p90 931 → 332; 반복 쌍 810 → 262), **목표 533 ms 안**, 74/74 청크 모두.

## "같다" 의 근거

### 1. 원소별 산술 — 같은 연산 · 같은 순서 · 하나씩 반올림

| 단계 | numpy (정의) | GPU |
|---|---|---|
| 배율 · valid | `d = depth*scale`; `isfinite & >0 & >=min & <=max` | 같은 곱 · 같은 double 비교 |
| 픽셀 순서 | `np.nonzero` (행 우선) | `torch.nonzero` (행 우선) |
| 카메라 x / y | `(col − cx) * z / fx` (int64 → f64 정확) | `__ddiv_rn(__dmul_rn(__dsub_rn(col, cx), z), fx)` |
| radial gate | `norm(axis=1)` = `sqrt((x²+y²)+z²)` (B2 실측 순서) | 원소별 kernel 따로, 같은 순서 |
| voxel key | `floor(p / float(vs))` | `floor(p / vs_t)` — **분모는 CUDA 0-d tensor** (스칼라면 torch 가 역수 곱으로 바꿈, B3: 100 만 중 13.3 만 1 ulp) |
| 대표점 | `np.unique(return_index)` (mergesort → 첫 등장) | `scatter_reduce(amin)` of index — 정수 |
| attention | `_resample` 의 (H, W) 맵을 `[v, u]` | 같은 1-D 표 (`y0 · y1 · wy · x0 · x1 · wx`) 를 `[v]`/`[u]` 로 색인해 같은 float32 식 (각 출력 픽셀은 자기 행/열 인자만의 원소별 식 — 축약 없음) |

### 2. `pts_cam @ R.T` 와 RANSAC 의 `pts @ normals[block].T` — numpy 가 부르는 BLAS 의 산술을 측정해 그대로

numpy 1.26.4 의 matmul 은 OpenBLAS 0.3.23 (DYNAMIC_ARCH, 이 기계 Xeon 6767P) 의 dgemm 을 부른다. 원소 하나는
`Σ_k p_k · r_k` 를 **k 순서의 FMA 사슬** `fma(z, r2, fma(y, r1, x·r0))` 로 계산한다 (그 뒤 `+ t` 는 numpy 의 별도 덧셈):

| 탐침 (`scratchpad/t38b4/blas_probe*.py` · `test_numpy_dgemm_is_the_fma_chain_the_kernels_compute`) | 결과 |
|---|---|
| `(N,3) @ R.T + t`, N = 5 … 505,824 (8 크기) | FMA 사슬 **0 개 다름**; FMA 없는 `(xa + yb) + zc` 는 N 의 50–60 % 다름 |
| `(N,3) @ (3,m)`, N = 2 … 69 · 1000 · 20,585 · 33,588 · 40,686, m = 2 … 32 (블록 슬라이스 view) | 0 개 다름 |
| N = 1 (행 하나) 또는 m = 1 (열 하나) | **다름** — numpy 가 gemv 로 감 |

그래서 (a) 역투영은 점 2 개 이상일 때만 GPU (1 개 이하 → numpy 경로), (b) RANSAC 은 폭 ≥ 2 블록만 GPU, 폭 1 꼬리 블록
(가설 수 ≡ 1 mod 32) 은 numpy 로 센다. 이것은 **정의가 아니라 측정된 사실**이므로 새 테스트가 매 실행 다시 잰다 — BLAS 가
바뀌면 조용히 어긋나지 않고 테스트가 깨진다 (테스트: 18 크기 × m 2…32 + 회전).

### 3. RANSAC — 가설은 그대로, 수는 정수

가설 (seed → `default_rng` → 삼중점 → 퇴화 제거 → `_plane_from_points` (cross · norm · einsum) → 각도 문턱) 은 **numpy 그대로**
라 같은 가설이다. GPU 는 가설별 inlier 수만 센다: 거리 = 위 dgemm 사슬, `− offset` · `abs` · `≤ thr` 는 IEEE 단일 연산,
수는 정수 → **같은 수**. 선택 규칙: 예전 블록 루프 (블록 안 `argmax` = 첫 최대, 블록 간 엄격히 큰 것만 갱신) = 전역 첫 argmax.
그 뒤 (최종 inlier · SVD refit · 재선택 · 방향) 은 CPU 그대로. **평면은 허용오차가 아니라 비트 단위로 같다** (normal 바이트 ·
offset hex · inlier index 배열 · rms hex).

### 4. self-filter 와 voxel 자르기

B2 의 판정 kernel (`(dx²+dy²)+dz² ≤ R²`, guard 는 `sqrt` 비교) 을 **같은 seam (`robot_sphere_mask`) 으로**, 점이 이미 있는
GPU 에서 돌린다. voxel 대표점의 keep/drop = 그 대표점 픽셀의 판정 (B2 의 `filter_cloud` 와 같은 규칙, 역투영 (u, v) → 점 1:1).
