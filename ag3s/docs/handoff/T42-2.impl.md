# T42-2 — implementation: varied black obstacles for the pick and the place phase (pi05_TO_hybrid)

> writer: ag3s-implementer (A1) · 2026-10-05 07:45 KST · readers: verifier, scribe, lead
> Not committed (the lead commits). Code base: pi05_TO_hybrid `bd6a002` + working-tree diff (2 files); main repo + 1 new test file.

## What was done (plain summary first)

There are four new obstacle slots. Each one is placed by the per-run config, with position, yaw and size keys, the same way `bar_height` works for the hurdle:
- **pick phase:** `post_0` (a post beside the fruit), `fence_0` (a low rail on two short legs) and `overbar_0` (a bar above the fruit on two legs);
- **place phase:** `crate_post_0` (a post beside the crate rim). The existing `hurdle_0` stays a place-phase slot.

All new slots are capsules and cylinders only, with no boxes.
- **Colour:** every obstacle's visual geoms, old slots included, are now **black** by default. Each config entry can set `"rgba"`, which recolours that slot's visual geoms only.
- **Collision geometry:** unchanged for the old slots.
- **`clear`:** bit-identical to `bd6a002`.

Sizes are set at run time, but the resulting model is the model MuJoCo would compile with those sizes. For every slot and size, every numeric `MjModel` array is bit-identical to an `MjSpec` compile, and MuJoCo's contacts are the same.
- **Where the distances come from:** the reset and stop checks reach every new slot through the T40 H certified `pair_distance`. Every pair matches an independent GJK.
- **Slots at once:** several slots can be active together, for example a pick and a place obstacle.

What the keys mean:
- `position` is the footprint centre on the table.
- `height` is the height of the post top above the table.
- `bar_height` is the height of the bar centre above the table.
- `length` is the distance between the legs, which is the bar's axis segment. The capsule adds its radius at each end.
- `yaw` turns the bar, which lies along local x. The legs stand at `position ± R(yaw)[length/2, 0, 0]` and reach from the table up to the bar axis.

`SLOT_PHASE` records each slot's intended phase. It is used for documentation only; where an obstacle actually goes is decided by the config.

### Config format (per-run JSON, same file as T40 E)

```json
{"version": 1, "table_surface_z": 0.82, "profiles": {
  "clear": {"scene": "any", "obstacles": []},
  "ep1828_post_and_crate_post": {"scene": "fruit", "obstacles": [
    {"slot": "post_0", "position": [0.625, 0.30, 0.82], "height": 0.20, "radius": 0.02},
    {"slot": "crate_post_0", "position": [0.64, 0.17, 0.82], "height": 0.26, "radius": 0.02,
     "rgba": [0.2, 0.2, 0.2, 1.0]}]},
  "ep1802_overbar": {"scene": "fruit", "obstacles": [
    {"slot": "overbar_0", "position": [0.557, -0.303, 0.82], "yaw": 0.0, "bar_height": 0.18, "length": 0.34, "radius": 0.012}]}}}
```

- **Validation:** a missing size key takes its default. A size key outside its range, NaN, inf, or used on a slot that does not take it raises `ValueError`. Examples of the last case: `height` on `fence_0`, or any size key on `bollard_*`.
- **`rgba`:** 4 values, each in [0, 1]. It is optional on every slot. When it is absent, the slot is black (`BLACK_RGBA` = 0.02 0.02 0.02 1).
- **Several obstacles:** one profile can list several obstacles, but each slot only once. Two or more can be active together.
- **Usage:** `--obstacle-config <json> --obstacle-profile <name>`. The client did not change.

### How sizes are set at run time (and why it is safe)

The obstacle model is compiled once, from the XML. A size can then only be changed by writing model arrays, so I built every resizable part so that a size touches as few compiled quantities as possible:
- Every resizable part is its own mocap body. Each body has exactly one collision geom, centred on the body origin, plus a visual twin of the same type and size.
- Each body also has an explicit `<inertial>`, so the inertial frame is the body frame.

With that layout, a size changes only four arrays: `geom_size`, `geom_rbound`, `geom_aabb`, and the body's single BVH node (`bvh_aabb`). I found this by diffing two `MjSpec` compiles that differ only in the size. Without the explicit inertial, `body_ipos`/`body_inertia` and the BVH frame would change as well.

The manager writes these four arrays with the compiler's formulas. The BVH extent is computed from the 8 corners rotated by `mju_rotVecQuat`. `|R| @ extent` comes out 1–3 ulp off on the rotated bars.
- **Checks at manager construction:** `_init_resizable` verifies the layout above. It also checks that the formulas applied to the XML sizes reproduce the compiled arrays bit for bit; any drift raises `RuntimeError`.
- **Parking:** `park_all` restores the compiled arrays exactly.
- **What is not updated:** `m.stat` `extent`/`center`/`meansize`. These are drawing statistics: the free-camera default and the marker scale. They keep the XML-compile values, as in any obstacle run. `meaninertia`/`meanmass`, which the solver uses, are identical.

## What the verifier needs to know

- **New flags or default changes:** no new flags.
  - **Default changes:** every obstacle is black, so **hurdle runs now show a black hurdle instead of the red/white/grey one** (T40 F/G/J configs). The bollards and divider are black too. A single `rgba` per entry cannot reproduce the old multi-colour look; only git `bd6a002` can.
  - **New config keys:** `height`, `radius`, `length` (and `bar_height` on `fence_0`/`overbar_0`), and `rgba`.
  - **New slots:** `post_0`, `fence_0`, `overbar_0`, `crate_post_0`.
- **Products to regenerate:** none. No npz or ESDF depends on this.
- **Compatibility with old records:** none broken.
  - `clear` is bit-identical (pinned).
  - Obstacle runs load a model with 8 more mocap bodies and 16 more geoms, all parked; qpos/qvel/ctrl are unchanged and old geom/body ids do not move.
  - Hurdle placement is bit-identical to T40 E/H (the on-axis offset is added exactly as before; `tests/sim/test_t40*.py` unchanged and passing).
  - `positions()` returns the config footprint; for the old slots this is the same value as before.
- **Run-time behaviour:** the manager changes `model` arrays at `activate()`, before the first policy step, and never during a run. Only one manager per model is supported. A second manager on a model left resized raises `RuntimeError` with instructions to call `park_all()` first.
- **Stop-check cost:** a new slot adds 1–3 collision geoms, fewer than the hurdle's 7. Every geom goes through the T40 H sorted, certified sweep.
- **Placement hints (from the smoke runs):**
  - The fruits sit at |y| ≈ 0.30–0.33 and the footprint validation allows |y| ≤ 0.35. Pick-phase posts therefore go on the ±x side of the fruit or on its crate side.
  - `overbar_0` at bar 0.18 over a right-arm fruit leaves only 28 mm robot clearance at reset. Lower bars, or a bar along y, may hit the 0.02 m reset margin.
  - `crate_post_0` close to the crate edge leaves only mm of object clearance (5 mm at (0.64, 0.17) on ep 1828). The crate handles at |y| ≈ 0.2 are payload geoms.
- **Untouched, outside the brief:** `pi05_infer.py --obstacle-config` help still says only "hurdle_0 takes position, yaw and bar_height". The format docstring it points to is up to date.

## What I expect

(The verifier reads this only after measuring.)
- On the T42-1 episodes, a pick obstacle placed on the recorded approach (post or fence beside the fruit, overbar over it) and a place obstacle on the recorded carry (crate_post at the rim, hurdle) will both pass the reset checks if they stay about 3 cm off the reset gripper pose and off the crate and handles.
- E0 probably hits or stops at the overbar more often than at the posts. The recorded top-down approach passes right through a bar placed over the fruit.
- The black colour should make obstacles stand out against the light table in the head and wrist images. Whether the policy's attention picks them up is for the runs to show.
