# T18 — 실행 피드백 계약: 서버가 "제안" 이 아니라 "실행된 것" 을 안다

> writer: lead (A0) · 2026-09-28 · 읽는 쪽: implementer, verifier
> 근거: [지침](AG3S_GRASP_FAILURE_IMPLEMENTATION_GUIDE.md) §6.3 · §6.4 · §8.1 · §10-1, [계획](AG3S_GRASP_FIX_PLAN.md)

## 왜 지금 이것인가

T16 에서 정책이 t=176 (0.0219) · t=208 (0.0258) 에 gripper 닫힘을 제안했지만 그 청크는 HOLD 로 실행되지 않았다.
서버는 그것을 모른다 — `_run_latch()` 는 **계획 청크의 첫 행** `chunk[0, gripper_col]` 을 gripper 신호로 읽고,
`safe_policy` 는 클라이언트 실행 결과를 알기 전에 refined 를 `_previous_chunk` 로 저장하며, `refiner._continuity_reference`
는 이전 청크의 앞 K 스텝이 실행됐다고 **가정**한다. HOLD·부분 실행이면 셋 다 틀린다 (지침 §6.4).

이 STEP 은 **사실을 실어 나르는 배관**이다. attach 의 의미를 바꾸는 것(T22)·게이트를 바꾸는 것(T23)은 이 위에 선다.

```
로컬 제어 루프 ──(직전 청크 실행 사실)──► 요청 ──► SafePolicy ──► latch · continuity · 기록
```

## 구현에 요청하는 것 (→ implementer)

### 1. 로컬 → 서버 피드백 (`wire.py` · `client.py` · `pi05_infer.py`)

다음 요청에 **직전 청크의 실행 사실**을 `ag3s/` 접두 키로 싣는다 (`pack_request` / `strip_request` 왕복, 테스트 필수).
키 이름은 네가 정하되 **정보의 소유권과 갱신 시점**을 지킨다 (지침 §9):

| 정보 | 뜻 |
|---|---|
| 직전 청크 seq | 어느 계획에 대한 사실인가 |
| 실행 step 수 / HOLD step 수 | 8 중 몇이 정책(refined) 청크로 실행됐나 |
| HOLD 사유 (`kind` · 문장) | `unsafe` · `timeout` · `stale` · `error` · 없음 |
| 적용된 gripper 명령 (양손, step 별 또는 마지막) | **실제 `d.ctrl` 에 들어간 값** — HOLD 면 `rby1_state()` 의 값 |
| 측정 gripper 개도 (양손, 정규화) | 촬영 시점의 `qpos` 기준. `build_obs` 와 같은 규약(1 = 열림) |
| 적용된 팔 목표 (선택) | step 별 `ctrl` 14 열 — drift 평가용 (지침 §8.2: ctrl 이 기록에 없어 drift 원인을 확정하지 못했다) |

`pi05_infer.py` 의 제어 루프에서 `apply_action` 직후 **실제 적용 action** 을 모아 두고, 다음 `safe_client.infer()` 호출 때 넘긴다.
`SafeRemoteClient` 가 그것을 `_pack` 에서 싣는다. 로컬 `frame_recorder.control(...)` 의 `extra` 에도 적용 action·gripper 를 남긴다.

**`pi05_infer.py` 는 `/mnt/dev/work/pi05_TO_hybrid/rby1_bringup/pi05_infer.py` (서버 사본) 을 고친다.** 로컬 PC 의
`~/dev_ws/vla/pi0_TO_ws/src/rby1_bringup/pi05_infer.py` 는 사용자가 동기화한다 — impl.md 에 **diff 를 그대로** 적어라.

### 2. 서버가 사실을 쓴다 (`safe_policy.py` · `refiner.py`)

- `SafePolicy.infer` 가 피드백을 `_pending` 에 두고, `_record` 가 constraint record 의 `summary_json` 에 싣는다
  (키 이름은 `exec_feedback` 계열로, 없으면 `null` 이 아니라 **키 자체를 싣되 `available: false`**).
- `_run_latch` 의 gripper 신호: **측정 개도(피드백)** 를 우선 쓰고, 피드백이 없으면 지금처럼 계획 첫 행을 쓰되 `note` 에
  `"gripper signal = planned (no feedback)"` 를 남긴다. latch 의 **판단 규칙은 바꾸지 않는다** (T22 의 일).
- `_previous_chunk` / `_continuity_reference`: 실제 실행 step 수 `n_exec` 로 정렬한다. `n_exec == 0` (HOLD) 이면 연속성
  참조를 **없앤다** (`None`), `0 < n_exec < K` 면 `n_exec` 만큼만 잘라 정렬한다. 지금의 "K 스텝 실행 가정" 은 피드백이 없을 때만 남긴다.
- 응답 `notes` 에 "피드백 수신: seq N, exec k/8" 한 줄.
