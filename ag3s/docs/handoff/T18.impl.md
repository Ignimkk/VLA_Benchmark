## 무엇을 했나 (평이한 요약 먼저)

**이제 로컬이 다음 요청에 직전 청크의 실행 사실을 실어 보낸다.** 몇 step 이 청크로 실행됐고 몇 step 이 HOLD 였는지,
실제 `d.ctrl` 에 들어간 gripper·팔 목표, 촬영 시점에 잰 gripper 개도가 들어간다. 키는 `ag3s/exec_feedback`
하나이고 그 안이 dict 다. 서버는 이 사실을 셋에 쓴다. (1) constraint record 의 `summary_json` 에 **언제나**
`exec_feedback` 을 싣는다 (없으면 `available: false` 와 `reason`). (2) latch 의 gripper 신호는 **측정 개도를 먼저**
쓰고, 피드백이 없을 때만 예전처럼 계획 첫 행을 쓰며 그때 `"gripper signal = planned (no feedback)"` 를 남긴다.
(3) 연속성 참조를 **실제 실행 수 `n_exec` 로 정렬**한다. HOLD(`n_exec == 0`) 뒤에는 연속성 참조를 없앤다.

latch 의 판단 규칙(문턱 0.85, 3 프레임)과 `should_execute` · `_hold` 의 게이트 의미는 바꾸지 않았다.
응답의 키 집합도 그대로다. 피드백은 응답 `notes` 에 한 줄로만 되돌아간다.

## 와이어 키 — `ag3s/exec_feedback` (요청, dict)

소유자는 로컬 제어 루프이고(`client.ExecutionLog` 가 `apply_action` 직후에 모은다), **청크 경계**에서 갱신된다.
정의는 `benchmark/trajopt/wire.py` 머리말의 `ag3s/exec_feedback` 절에 있다.

| 안쪽 키 | 형 | 뜻 |
|---|---|---|
| `available` | bool | 사실이 실렸나. `False` 면 `reason` 만 있다 |
| `reason` | str | `available=False` 의 이유 — 첫 청크 / 호출부가 안 넘김 / **옛 클라이언트(키 없음)** / `malformed ...` |
| `seq` | int | 어느 계획에 대한 사실인가 (그 청크를 받은 요청의 `ag3s/seq`) |
| `t_step_start` | int | 그 청크의 첫 제어 step (로컬 `t_step`) — T16 의 t=176·208 과 맞출 때 쓴다 |
| `n_steps` · `n_exec` · `n_hold` | int | 돈 step 수 · 계획 행을 적용한 수 · HOLD 수 (`n_hold = n_steps − n_exec`) |
| `executed` | list[bool] `[n_steps]` | step 별 실행 여부 (부분 실행의 모양) |
| `executed_chunk` | str | `refined` · `reference` · `none`(= HOLD) |
| `ipc` | str | 그 왕복의 결과 `ok`/`unsafe`/`timeout`/`stale`/`error` |
| `hold_kind` | str \| None | HOLD 사유 종류 (`wire.HOLD_KINDS` = `unsafe`·`timeout`·`stale`·`error`). 실행했으면 `None` |
| `hold_reason` | str \| None | HOLD 사유 문장 (`SafeRemoteClient.last_reason`) |
| `planned_gripper` | float32 `[n_steps, 2]` | 그 step 에 계획 청크가 **말한** (왼, 오른) gripper, 정규화 |
| `applied_gripper` | float32 `[n_steps, 2]` | **실제 `d.ctrl`** 의 (왼, 오른) gripper ÷ `RBY1_GRIPPER_OPEN` (1 = 열림). HOLD 면 `rby1_state()` 값 |
| `applied_arm` | float32 `[n_steps, 2N]` | 실제 `d.ctrl` 의 팔 목표 `[왼 N, 오른 N]` (drift 평가용, 지침 §8.2) |
| `measured_gripper` | float32 `[2]` | 이번 요청 **촬영 시점**의 `qpos` 로 잰 (왼, 오른) 개도, `build_obs` 규약 (1 = 열림) |

- **키 없음 ≠ `available=False`.** 키가 없으면 옛 클라이언트이고, 새 `SafeRemoteClient` 는 낼 사실이 없어도
  `no_exec_feedback(reason)` 을 싣는다. 모양이 틀리면 서버는 예외를 내지 않고 `available=False` + `malformed ...` 로 받는다.
- **크기:** 8 step 이면 배열 합 584 B 다. 그래서 step 별 `applied_arm` 까지 와이어에 싣는다 (task "되돌아올 지점" 은 해당 없음).

### 서버 기록 (`summary_json`, 청크마다 셋 다 언제나)

| 키 | 무엇 |
|---|---|
| `exec_feedback` | 위 dict 를 JSON 으로 바꾼 것 (배열은 리스트로) |
| `exec_continuity` | `plan_seq` · `feedback_seq` · `n_exec` · `mode` · **`previous_chunk`** (`"refined"`/`"reference"`/`null`) · `used` · `aligned_from_step` · `source` |
| `exec_latch_signal` | `hand` · `source` (`measured`/`planned`) · `value` · `planned_first_row` · `note` (latch 가 안 돈 프레임에서는 `{}`) |

### 로컬 frame 기록 (`frames.jsonl`, 값이 주어졌을 때만 키가 생긴다)

| 프레임 | 키 | 무엇 |
|---|---|---|
| planning | `exec_feedback` | 그 요청이 실어 보낸 dict (`SafeRemoteClient.last_exec_feedback`) |
| control | `applied_ctrl` | `{"arm": [2N], "gripper": [왼, 오른]}` — 그 step 에 실제 `d.ctrl` 에 들어간 값 |

### 응답 `notes` 에 더해지는 줄 (응답 키 집합은 그대로)

- `피드백 수신: seq N, exec k/8` — HOLD 가 있었으면 뒤에 ` (HOLD unsafe: 8 steps)` 가 붙는다. 피드백이 없으면 `피드백 없음: <reason>`
- 연속성 참조를 버렸으면 `continuity reference dropped: <이유>`
- latch 가 계획값을 썼으면 `gripper signal = planned (no feedback)`

## 연속성 정렬 규칙 (`SafePolicy._continuity_input` → `refiner._continuity_reference`)

| 피드백 | 이전 청크 | refiner 에 넘기는 `previous_executed_steps` | 결과 |
|---|---|---|---|
| 없음 | `_previous_chunk` (예전 기본값) | 키 없음 | 인덱스 K 부터 (예전 그대로, `source: assumed`) |
| seq 가 계획 캐시와 다름 | `None` | — | 연속성 항 없음 |
| `n_exec == 0` (HOLD) | 캐시 | `0` | `None` (`previous_chunk: null`) |
| 앞에서부터 `k` step 실행 | 로컬이 **고른** 쪽 (`refined`/`reference`) | `k` | 인덱스 `k` 부터 |
| 실행이 앞에서부터 이어지지 않음 | `None` | — | 연속성 항 없음 |

계획 캐시(`_previous_plan = {seq, refined, reference}`)와 기본값(`_previous_chunk`)을 나눴다. 기존 테스트가 읽는
`_previous_chunk` 의 뜻(closed = refined, shadow = reference)은 그대로다.
