## What was done (plain summary first)

The 16D model with an obstacle profile now loads the fruit/crate obstacle scene instead of the block scene (the T40 A blocker,
`apple_free missing`, is gone). There is a new slot, `hurdle_0`: a red-and-white capsule bar 0.264 m long on two
posts, built from capsules and cylinders only. A per-run JSON sets its position, yaw, and **bar height (0.20–0.32 m above the
table)**. The height is set by moving two mocap bodies that telescope, so the compiled model never changes.
`--obstacle-profile clear` (the default) is still the old scene, byte for byte.
On distances, `mj_geomDistance` is correct for every hurdle pair type except **capsule–box**, where MuJoCo 3.11 reports a
positive distance for about 5 % of overlapping pairs (up to 34 mm). Capsule–box pairs now use an exact computation.

### How the bar height works (and why this way)

The prop is two mocap bodies. One sits on the table: the feet and the fixed sleeves. The other sits at the bar centre: the bar
and sliding posts that reach 0.150 m down. `activate()` moves the second body to `position + bar_height` with the same yaw.
Across 0.20–0.32 m the bottom of the sliding post, at `bar_height − 0.150`, stays inside the sleeve (z 0.05–0.17 vs a sleeve
top of 0.18), so the post looks continuous and collides as one piece. Both bodies are mocap bodies (welded to the world),
so they never collide with each other or with the table.

I rejected resizing the post geoms at run time. That would leave `geom_rbound`, `geom_aabb` and the body BVH (`bvh_aabb`) as
they were at compile time, and both the broad-phase and `mj_geomDistance` read those values.

### Config format (per-run JSON)

```json
{"version": 1, "table_surface_z": 0.82,
 "profiles": {"clear": {"scene": "any", "obstacles": []},
              "ep1807_hurdle": {"scene": "fruit", "obstacles": [
                 {"slot": "hurdle_0", "position": [0.68, 0.23, 0.82], "yaw": 0.0, "bar_height": 0.26}]}}}
```
- `position` is the footprint centre `[x, y, table_z]`.
- `yaw` rotates about world z. The bar lies along local x, so `yaw = 0` puts the bar along world x.
- `bar_height` is the height of the bar centre above `position[2]`.

Usage:
- Add the hurdle: `--obstacle-config <json> --obstacle-profile ep1807_hurdle`.
- Remove it: `--obstacle-profile clear`, or leave both flags out.

## What the verifier needs to know

- **New flags or default changes:** none. New config field: `bar_height` (hurdle only). The new slot is `hurdle_0`.
  `--obstacle-profile clear` is unchanged.
- **Overlap sign:** `pair_distance` and the two clearances return ≤ 0 on overlap. `mj_geomDistance` returns exactly 0.0 for some deep
  mesh overlaps, and `capsule_box_distance` returns a negative depth measure, not MuJoCo's penetration depth. The checks only use
  `<= stop_distance` and `<= 0`.
- **Behaviour change for existing slots:** the bounding-sphere prefilter is mathematically neutral. The one case where it could differ
  is a far-apart box pair for which `mj_geomDistance` was wrong (divider_0, T40 A). There it moves the value toward the truth.
  Bollards gave the same values (test (e)).
- **Placement fact (ep 1807, for F):** at reset the left gripper hangs at x 0.43–0.48, y 0.21–0.26, 0.21–0.30 m above the table.
  That is inside the apple → crate corridor and at bar height, so a bar across the corridor at reset collides with the gripper
  (e.g. (0.55, 0.215) → robot clearance −19 mm for every bar height). The crate handles reach y ≈ 0.19. The smoke placement
  (0.68, 0.23, yaw 0, bar 0.26) passes the reset checks (robot/object 0.040/0.022 m), but it only crosses the carry line at the bar end.
- **Smoke images:** `outputs/verify/T40/E/smoke_ep1807_hurdle_{front,oblique,zed_left}.png`. These come from `main()` up to the policy
  call, with no server. They are not figures under `docs/figures`; those are the verifier's.
- **Still broken (not fixed, outside the brief):** `pi05_TO_hybrid/rby1_bringup/pi05_ex_infer.py:1215-1219` has the same 16D → block-XML branch.
- **Products to regenerate:** the T40 A dry-check configs no longer need the `--cf-transport-xml` counterfactual. No npz files.
- **Compatibility with old records:** none broken. Obstacle-profile runs load a model with 2 more mocap bodies and 25 more geoms,
  all parked; qpos is unchanged.
