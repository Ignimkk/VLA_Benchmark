# T9 — 구현

> writer: ag3s-implementer (A1) · 2026-09-26 · 읽는 쪽: verifier, scribe, lead

## 무엇을 했나 (평이한 요약 먼저)

**closed loop 응답도 정책 원본 청크를 싣는다.** 그래야 *"TO 가 청크를 얼마나 바꿨나"* 를 닫힌
고리에서 잴 수 있다. 충돌 제약이 더 이상 아무것도 막지 않는 판(39 chunk 전부 `safe`)에서도 TO 가
청크를 고치므로, **남은 변형은 전부 목적함수가 만든 것**이고 그 크기를 재려면 `actions`(refined)
옆에 원본이 있어야 한다. 같은 결핍에 다섯 번 막혔다.

**막고 있던 것은 키 하나가 두 뜻을 겸한 것이었다.** `actions_reference` 의 **있음/없음**이
*"서버가 shadow 모드인가"* 의 유일한 신호였고, 그래서 closed loop 이 그 키를 실으면 로컬이
*"서버는 shadow 인데 나는 아니다"* 로 읽고 **즉시 죽는다.** 겸직을 끊었다 — 모드는 새 응답 키
`shadow` 가 **명시**하고, `actions_reference` 는 데이터일 뿐이다.

**shadow 는 여전히 shadow 다.** `--safe-shadow` 의 거절은 한 줄도 느슨해지지 않았고, 근거만
*"reference 가 왔나"* → *"서버가 shadow 라고 말했나"* 로 옮겼다. 새 테스트 12 개가 네 조합
전부와 옛 서버에 대한 물러남까지 지킨다.

**목적함수 가중치 넷을 CLI 로 뺐다** (`--w-track` · `--w-smooth` · `--w-continuity` ·
`--w-slack`). 기본값은 하나도 안 바꿨고, 준 것만 config 에 들어간다.

---

## 두 가지를 갈라 적는다 — 이게 헷갈리면 기록이 거짓이 된다

| | `actions_reference` 를 **싣는다** (T9) | `--shadow` / `--safe-shadow` |
|---|---|---|
| 무엇 | 원본 청크를 **기록에** 싣는다 | 로봇이 원본 청크를 **실행한다** |
| 로봇이 실행하는 것 | **refined** (닫힌 고리 그대로) | **reference** |
| 언제 | 언제나 | flag 를 줄 때만 |
| 응답의 `shadow` 키 | `False` | `True` |
| 짝 검사 | 없음 (모드가 아니다) | 안 맞으면 **즉시 죽는다** |

서버 시작 로그가 이 구분을 한 줄로 말한다:

```
response carries 'actions_reference' on every chunk (T9): the policy's ORIGINAL chunk rides next
to the refined one so 'how much did TO change it' is measurable in closed loop too. This is NOT
shadow mode — the robot still executes the refined chunk. Mode is declared separately as
'shadow'=False. Cost: a planning record row grows from ~19.8 KB to ~36.7 KB.
```

## 크기 영향 (실측)

**와이어** — `msgpack` 으로 직접 재었다 (`float32` 청크 하나가 추가된다):

| 청크 길이 | T9 이전 | T9 이후 | 증가 |
|---|---|---|---|
| `H = 8` (실행 창) | 905 B | 1,478 B | **+573 B** |
| `H = 50` (전체 청크) | 3,593 B | 6,854 B | **+3,261 B** |

15 Hz · 청크당 한 번이면 `H = 50` 에서 초당 약 1.5 KB 다. **기록**쪽 증가가 훨씬 크다 —
지시서가 인용한 대로 planning 한 줄이 **19,837 B → 36,704 B**(shadow 수준)가 된다. 로컬
기록(`pi05_infer.py:1558`)이 `last_actions_reference` 를 그대로 적으므로 **코드 변경 없이**
자동으로 채워진다. 그 값을 아는 채로 고른 것이다: 같은 결핍에 여섯 번째로 막히는 것이 더 비싸다.

## 내가 기대하는 결과

> **verifier 는 측정이 끝나기 전에 이 절을 읽지 않는다.**

이 STEP 은 **측정 도구**이지 수정이 아니다. 그래서 기대는 "숫자가 좋아진다" 가 아니라
**"닫힌 고리에서 refined − reference 를 처음으로 볼 수 있다"** 하나다.

그 값이 보이면 갈림길이 둘이다.

1. **실행 창 안의 차이가 크다** (지시서가 인용한 중앙값 2.6° · 최대 8.8° 수준이 그대로 나온다)
   → 원인은 목적함수다. 가장 유력한 항은 `w_continuity` 인데, 그 항은 **앞 청크의 꼬리**를
   붙잡으므로 정책이 파지 순간에 손목을 급히 꺾을 때 그것을 **직전 청크 쪽으로 되당긴다.**
   `--w-continuity 0` 이 첫 시험이고, 그 다음이 `--w-smooth 0` 이다 (2 차 차분 항은 같은 급한
   변화를 다른 방식으로 깎는다). `w_track` 은 **올리는** 쪽으로 시험해야 한다 — 내리면 TO 가 더
   자유로워지고, 지금 문제는 자유가 부족한 것이 아니다.
2. **차이가 사실상 0 인데도 shadow 는 성공하고 closed loop 은 헛잡는다** → 원인은 청크의 값이
   아니라 **타이밍**이다. 그때 봐야 할 것은 refiner 의 실행 창(`plan_horizon`)과 grasp latch
   이고, 목적함수를 훑는 것은 시간 낭비다.

어느 쪽이든 **이 STEP 자체가 궤적을 바꾸면 안 된다.** 39 chunk 전부 `safe` 라는 직전 결과가
그대로 재현돼야 하고, 안 그러면 `actions` 경로에 무언가 섞인 것이므로 그것을 먼저 봐야 한다.
