# T40H — implementation: no more false-zero obstacle distance in the client (pi05_TO_hybrid)

> writer: ag3s-implementer (A1) · 2026-10-05 07:00 KST · readers: verifier, scribe, lead
> Not committed (the lead commits). Code base: pi05_TO_hybrid `98e07d6` + working-tree diff; main repo `54399b8` + new test files.

## What was done (plain summary first)

All 5 false-zero stops reproduce **bit for bit**, including ep1967. I replayed each run from `main()` reset (`--warmup-steps 1000`)
with the recorded `applied_ctrl`, sub-step by sub-step. Every recorded control row's qpos matched exactly (0 of 429 rows differed),
and the stop check fired at the recorded step.

**Root cause (one cause, all 5 runs):** MuJoCo 3.11 `mj_geomDistance` (nativeccd GJK) returns exactly **0.0** for a hurdle **foot**
(a flat cylinder, r 35 mm × 12 mm, vertical axis) vs an arm/finger **mesh** that is 0.070–0.236 m away (GJK).
- It returns 0.0 in both argument orders whenever `distmax` exceeds the true gap. Below the gap, MuJoCo's cut-off exit fires first and the capped value is right.
- The returned witness points are 0.07–0.47 m apart, so the 0.0 is not a contact. GJK concluded "origin enclosed" on a degenerate simplex.
- The prefilter is not involved.
- The probe missed ep1967 because the failure needs the exact pose. It happens only at the sub-step state the stop check sees, never at the 429 recorded control rows,
  and only for a measure-small set of poses (the probe's ±2 mrad perturbations hit it 0–10 times in 400).
- After `mj_step`, `geom_xpos` belongs to the *pre-integration* qpos. Rebuilding the state from the post-step qpos does not reproduce it.

The T40 A divider "reset object clearance 0.0, GJK 117 mm" is the same failure, in box–box and box–mesh pairs.

**Fix:** the manager no longer trusts a raw `mj_geomDistance` value.
- **Positive value:** it is kept only if a cheap certificate passes. The witness points must be `value` apart and lie on the two exact supporting planes
  of their direction. The plane gap is a lower bound, so an under-estimate cannot pass.
- **Failed certificate, or a claimed overlap:** an exact GJK in numpy decides. It is new code, written so that a flat tetrahedron is never taken as enclosing the origin.
- **The minimum:** pairs are now swept in bounding-sphere order, with `distmax` set to the running checked minimum. This is also faster than before.

## What the verifier needs to know

- **New flags or default changes:** none. The `pair_distance` / `robot_clearance` / `object_clearance` signatures and the ≤ 0-on-overlap convention are unchanged.
- **Overlap values:** for a real overlap, the value is MuJoCo's raw depth, or `capsule_box_distance`'s negative measure, as before.
  A false overlap claim is replaced by the GJK distance.
- **J reruns:** they need a new snapshot that contains both files:
  - `pick_place_obstacles.py`;
  - the new `convex_distance.py` (an untracked file, so the lead must `git add` it).
- **J reruns, conditions:** rerun the 5 runs with the same seed, configs (`F/configs/*_r1.json` for C, `*_r2.json` for D), gate off and `--obstacle-stop-distance 0`.
  Nothing else changes, so a rerun is bit-identical to the T40 G record up to the old stop step. After it, the run continues.
- **Replay tool:** `outputs/verify/T40/H/replay.py` replays any T40 G run on CPU in about 5 s (`main()` reset + recorded `applied_ctrl`). Use it to check the snapshot before the GPU reruns.
- **Products to regenerate:** none. No npz or ESDF depends on this.
- **Compatibility with old records:** the T40 G records are unchanged. Their `min_robot_clearance_m` = 0.0 is the false value. The true values at the stop states are in the table above.
- **Speed:** the stop check costs 0.33–0.79 ms median per run, vs 2.7–5.1 ms for the old code at the same states.
- **Untouched, outside the brief:** `pi05_ex_infer.py:1215-1219` still has the 16D → block-XML branch noted in T40 E.

## What I expect

- None of the 5 reruns stops at t 103 / 137 / 23 / 71 / 90 with clearance 0.0. Each one continues past that step.
